Article 01 · Matching logic

Matching ingredients without making people type perfectly

If an app only understands an ingredient when somebody types it exactly the way the data expects, the app is making the person adapt to the code. I wanted PantryPal to do the opposite.

The main idea behind PantryPal is simple: tell it what food you already have and see what you can make. The annoying part is that ingredient names are not simple at all. A person can type apple, apples, Apples, or APPLES and mean exactly the same thing. Recipe data can also use slightly different forms of an ingredient, which means a straight string comparison can miss matches that are obvious to a person.

I normalize before I compare

The first thing I do is normalize ingredient input. I trim extra spacing, ignore capitalization, and reduce common variations to a consistent key before the matching logic runs. I also use the same normalization on the recipe side. That matters because normalizing only what the user types does not help if the recipe data is still being compared in a completely different form.

I kept the visible ingredient name separate from the comparison key. That lets the interface show a normal, readable label while the matching code works with a predictable value. It also keeps display concerns from leaking into the logic.

The rule I used:

Store the useful human-readable value, but compare a normalized key. Do not make the user memorize the spelling or format used by the dataset.

An exact usable recipe should beat a prettier partial match

Once ingredient names can be compared reliably, ranking becomes the next problem. A normal percentage score can look useful but still produce a bad recommendation. If one recipe uses everything in the pantry but another has a slightly higher weighted score and needs three extra ingredients, the second result may be less useful in the real situation.

So PantryPal treats complete matches as their own priority. Recipes the user can make with what they already have come first. After that, the user can decide how many missing ingredients are acceptable. Someone trying to spend nothing can choose no extra ingredients. Someone who is willing to pick up one or two things gets a wider set of results without being buried in recipes that require half a grocery trip.

The missing-ingredient count is more useful than a vague score

I still show match information, but I do not rely on a percentage by itself. “You have 8 of 10 ingredients” and “2 ingredients are missing” tell somebody what the recommendation actually means. That is a much more practical decision than asking them to interpret whether an 82% match is good enough.

This also made the grocery workflow easier later because the app already knows which ingredients are missing. The same information can continue into planning instead of being thrown away after the recipe card is rendered.

Quick-add ingredients are part of the matching feature

Input friction matters here too. If somebody has to type thirty common pantry items one at a time, the matching logic can be perfect and the feature can still be annoying to use. I added a set of common ingredients that can be toggled with one tap, while keeping the normal input for anything that is not listed.

The important part is that both paths go through the same normalization and storage logic. I did not want “quick add” to become a second version of the ingredient system with slightly different behavior.

What I would keep in any similar app

If I were building another search or recommendation feature from user-entered data, I would keep the same approach: normalize at the boundary, preserve the original display value, rank around the user’s real decision, and expose the reason a result is being shown. A recommendation is a lot easier to trust when the interface can explain it.

Article 02 · Connected workflows

Building a grocery list that does not make people buy food twice

A grocery list is easy to generate badly. Copying every ingredient from every planned recipe technically creates a list, but it ignores the most useful information PantryPal already has: what is in the kitchen.

I wanted the planner and grocery list to feel connected instead of looking like separate features that happen to live in the same app. If a person adds eggs, rice, onions, and cheese to their pantry, plans three meals, and then opens the grocery page, PantryPal should not tell them to buy those same ingredients again.

I treat the grocery list as a difference, not a copy

The generated grocery list is based on what planned recipes require minus what the user already has. That sounds obvious when it is written out, but it changes the whole implementation. The grocery page needs access to the planner data, recipe ingredients, and normalized pantry inventory. It cannot be a standalone checklist if I want it to produce a useful result.

The same ingredient matching rules have to be reused here. If the inventory says “tomatoes” and a recipe uses “tomato,” a simple text comparison could incorrectly add tomatoes to the grocery list. Shared normalization prevents the pages from disagreeing about the same ingredient.

What made the feature click:

The grocery list should answer “What am I missing?” instead of “What do these recipes contain?” Those are not the same question.

Generated items and manual items need to coexist

Meal ingredients are not the only things people buy. A useful grocery list also needs cereal somebody wants even though it is not attached to a recipe, cleaning supplies, snacks, pet food, drinks, or whatever else needs to come home. That is why PantryPal keeps manual grocery items alongside generated ones.

I also keep checked state persistent so the list does not reset because the page refreshed. Completed items can be cleared, and the list can be printed or exported. None of those pieces are complicated by themselves, but together they are what make it work outside of a demo click-through.

I did not want automation to take control away

Automatically generating a list is useful only if somebody can still understand and change it. I avoided treating the generated output as untouchable. The user can add what the app does not know about, check items off normally, and regenerate as their planning changes.

That is a pattern I would use in other apps too. Automation should remove repetitive work, not create a mystery state where the person has no idea why something happened.

The data should keep working after the first screen

This is one of the parts of PantryPal I care about most because it is where the project stops being a collection of pages. Ingredients influence recipe recommendations. Recipes go into the planner. The planner and pantry determine groceries. Favorites and custom recipes feed back into the same flow. Each step uses information the person already entered instead of asking for it again.

That kind of continuity is easy to miss when building one page at a time. I found it more useful to think in workflows: what is the person trying to do next, what does the app already know, and how much of that next step can be completed without another round of input?

Article 03 · Data quality

Why recipe data quality matters more than having a huge recipe count

A recipe library can have thousands of rows and still feel broken if the ingredients are incomplete, the instructions are weak, or the photo belongs to an entirely different meal.

Recipe data was one of the parts of PantryPal that forced me to stop looking at quantity as the main measure of progress. A big library sounds impressive, but the number does not matter much when somebody opens a recipe and the image is wrong or the ingredients do not line up with the dish.

A food photo is data, not decoration

At first it is tempting to treat recipe images as a visual layer. In practice, the image is making a claim about the recipe. If the card says chicken casserole and shows a hamburger, the result looks unreliable before the user even reads it.

I changed the image workflow so exact dish matches are preferred and broader fallbacks are only used when a better match cannot be resolved. Photo attribution is also retained rather than separating the image from its source information. That makes the image system more work, but it also means the app has a way to explain where the image came from.

Fallbacks need rules

External data sources are useful, but blindly accepting the first result is not. PantryPal can use external recipe data when built-in results are not enough, but the returned recipe still needs to be compared against the user’s ingredients and ranked using the same logic as local recipes. Otherwise the fallback becomes a completely different experience.

I use progressively broader image searches for the same reason. Start with the exact recipe name, then add food context or leading ingredients if needed. A fallback should widen the search without abandoning what the original request meant.

The data-quality lesson:

A fallback is not just “anything is better than nothing.” It needs acceptance rules, source information, and a clear point where the app should admit that it does not have a strong match.

The interface has to survive imperfect media

Even a correct remote image can load slowly, arrive with a strange aspect ratio, or fail later. I made the recipe cards and detail views constrain the image area so the photo cannot expand over text or change the whole layout. Lazy loading and caching reduce unnecessary requests, while error handling keeps a failed image from breaking the card around it.

This is the kind of thing that is easy to miss when testing with a few perfect images on a desktop. It became much more obvious once I looked at lots of recipes and smaller screens.

More data increases the need for validation

As a dataset grows, edge cases stop being edge cases. A weird ingredient name, missing field, duplicate recipe, or bad image mapping that only affects one percent of records can become dozens of visible problems. That is why I added more defensive handling instead of assuming every record would be shaped exactly the same way.

I also keep custom recipes separate from the built-in data and combine them through a single recipe-access path. That lets the rest of the app work with both without mutating the base collection.

What I would do before adding another thousand recipes

I would improve validation, source quality, and match confidence before chasing a bigger number. I would rather have fewer recipes that are accurate and easy to use than a huge library that makes somebody double-check everything outside the app. For a tool built around helping people decide what to cook, trust is part of the feature.
