Case Study

PantryPal: planning meals around what is already in the kitchen

I built PantryPal around a problem I run into in real life: there can be plenty of food in the house and still be no obvious answer to “What can I make without buying a bunch more stuff?”

Project snapshot

A connected meal-planning workflow

PantryPal keeps pantry inventory, recipe matching, meal planning, groceries, favorites, and custom recipes connected so information entered once can keep doing useful work.

01 · Problem

I did not want another recipe search that starts with knowing the answer

A lot of recipe tools start by asking what somebody wants to cook. That is useful when the meal is already decided, but it does not solve the situation I actually cared about. I wanted something for the nights when I am looking at food I already bought and trying to figure out what can be made from it.

The basic problem became: How can I turn a messy list of ingredients somebody has at home into useful meal options without making them do more work than the app saves?

That immediately made the ingredient inventory more than a side feature. It had to drive recommendations, keep affecting the planner, and prevent the grocery list from suggesting things the person already owns.

02 · Goals

I defined the project around a few things the app had to do well

Use what is already there first

Complete pantry matches should be easier to find than recipes that need several extra purchases.

Handle normal human input

Ingredient matching should not break because of capitalization, plurals, or small formatting differences.

Respect a real budget

Someone should be able to say they cannot buy anything else, or only allow a small number of missing ingredients.

Keep features connected

Pantry data, recipes, planning, and groceries should share information instead of behaving like unrelated tools.

03 · Ingredient matching

The matching logic had to understand intent, not exact typing

The first technical problem was ingredient normalization. A person should not get different results because they typed “Apple” instead of “apples.” I normalize ingredient values before comparison and use consistent keys for matching while keeping readable names for the interface.

I also added quick-select common ingredients because correctness is not enough if entering the pantry feels like filling out a spreadsheet. Typed ingredients and quick-add ingredients go through the same storage and normalization path so they behave consistently.

For ranking, I prioritize recipes that can be made with what the user already has. Partial matches come after that and can be limited by how many additional ingredients the user is willing or able to buy. I found that much more useful than treating a generic match percentage as the main answer.

Decision

Make “Can I actually make this?” more important than “How mathematically similar is this recipe to my pantry?”

04 · Connected workflow

I wanted each step to reuse information from the one before it

Once somebody finds a recipe, the next likely job is planning it. Once meals are planned, the next likely job is figuring out what needs to be bought. That gave me a clear workflow instead of a list of disconnected features.

Recipes can be added to the planner, and planned meals feed the grocery calculation. Before an ingredient becomes a generated grocery item, PantryPal checks it against the pantry inventory. The goal is to build the gap between what the meals require and what the user already has, not duplicate the entire ingredient list.

I kept manual grocery items too because a household buys plenty of things that are not tied to a planned recipe. Generated and manual items share the same usable checklist, checked state, printing, and export flow.

Favorites and custom recipes use the same recipe interactions, which means a recipe somebody adds themselves can still participate in planning instead of living in a separate dead-end section.

05 · Recipe data

A large recipe collection was only useful if the individual recipes were trustworthy

Recipe data ended up needing more attention than I expected. A big recipe count does not help if images are mismatched, ingredients are incomplete, or the instructions are not useful. I treated those as data-quality problems instead of cosmetic issues.

For recipe photos, PantryPal prefers an exact dish match and keeps source and license information with the resolved photo. Broader searches are fallbacks rather than the first choice. The layout also constrains image areas so a slow, oversized, or failed remote image cannot cover the recipe text.

External recipe fallback follows the same idea. It is there to widen the available results when local matches are not enough, but returned recipes still need to be ranked against the pantry. I did not want the app to switch from thoughtful local matching to a completely unrelated search experience just because a fallback was used.

06 · Mobile use

I kept checking the app from the place it would actually be used

A meal-planning app is very likely to be used on a phone, sometimes while standing in a kitchen or walking through a store. That made responsive behavior part of the functionality, not a final styling pass.

I checked navigation wrapping, recipe-card text, image sizing, planner controls, grocery interactions, dialog width, and tap targets at smaller sizes. One of the recurring problems was making sure photos stayed inside their own area instead of overlapping content. Another was keeping controls usable without turning every page into a cramped stack of tiny buttons.

The interface keeps the playful poster look, but the functional areas still need clear contrast, predictable spacing, and readable text. I tried to keep the personality in the visual system without letting it make routine tasks harder.

07 · Testing & refinement

The useful changes came from testing complete workflows, not isolated screens

I found more problems by following real sequences than by checking a page on its own. I would add pantry items, find a recipe, change the missing-ingredient allowance, plan the recipe, open groceries, check items off, refresh, and then go back to see whether the state still made sense.

That exposed issues such as inconsistent ingredient forms, generated groceries that should have been excluded, image failures, responsive navigation problems, and state that needed to persist across page changes. It also made me look harder at empty states. A page should explain what to do next when there is no data instead of just looking broken.

I also reviewed the code itself for the same kind of accumulated friction. I replaced dated “fix” filenames with stable production names, corrected broken asset references, organized historical QA notes away from the project root, and checked internal links, duplicate IDs, JavaScript syntax, and asset paths.

08 · Outcome

PantryPal now works as one workflow instead of a set of meal-planning pages

The final direction is much closer to the problem I wanted to solve. The pantry is the starting point. Recipe matches explain what the user has and what is missing. Budget limits can narrow the results. Recipes can move into planning, planning can produce groceries, and groceries take the existing pantry into account.

The biggest lesson for me was that useful software often comes from the connections between features. Inventory, search, planning, and a checklist are all common ideas. The value comes from making them share the right information at the right time and removing work from the next step.

If I continue the project, the next improvements I would prioritize are stronger automated validation of recipe/photo pairings, more robust ingredient synonym handling, and optional account-backed sync for people who want the same pantry and plan across devices. I would keep the current local-first behavior as a simple option rather than making an account mandatory.
